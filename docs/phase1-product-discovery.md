# Product Discovery — 找餐廳網站

> **SDLC Phase 1 — 需求發想**
> 依 `product-discovery` skill 的 5 個步驟整理。

## 1. 原始需求清單

- 想做一個找餐廳的網站
- 核心動機：現有服務（Google Maps / Yelp / IG）篩不到真正想要的餐廳、缺乏個人化整理能力
- 目標使用者：一般消費者
- 使用情境：當下要決定吃什麼（即時查詢）
- 額外痛點：平常在 IG、Google Maps 上滑到有興趣的餐廳，想加入口袋名單，但這些平台缺乏方便的收藏機制；就算手動記下來，也難以用自己的分類邏輯整理、之後搜尋
- 核心功能方向：搜尋+篩選、評論評分、地圖視覺化（三者皆需要）
- 特殊功能需求：自訂標籤，同時支援「個人整理用」（如：約會、家庭聚餐、一人食）與「公開特色標記用」（如：辣度、氛圍）
- 地理範圍：使用者指定的城市或更小區域，非全國性
- 平台範圍：先做網站，不做 App
- 專案定位：先做出來驗證想法（MVP/原型），不追求一次到位
- 明確排除：不想串接 Google Places API 等付費地圖服務，避免產生費用（至少 MVP 階段）
- 新增餐廳資料的方式：希望比手動打字方便，但不想產生 API 費用 → 收斂為「複製店名+地址等文字區塊，系統簡單解析預填」

## 2. 問題陳述 + 商業目標

**問題陳述**：
一般消費者有兩類相關痛點：
1. 平常在 IG、Google Maps 等平台瀏覽時看到有興趣的餐廳，缺乏方便的收藏機制，就算手動記下來也無法用自己的分類邏輯整理。
2. 當下要決定吃什麼時，現有工具（Google Maps / Yelp / IG）難以依自己的分類/條件精準篩選到真正想去的餐廳。

兩者共同指向：使用者需要一個**可自訂標籤整理、且能快速篩選查詢**的個人餐廳口袋名單系統。

**商業目標**：
做出一個以「跨平台收藏 + 自訂標籤整理 + 精準篩選」為核心的個人化餐廳口袋名單網站原型，驗證這個模式能否解決使用者「看到想收藏」與「想吃時篩選不到」這兩端的問題，是否有人願意持續使用。

## 3. 使用者與情境描述

**主要使用者**：一般消費者（會外食、平常會滑 IG / Google Maps 看到餐廳資訊的人）

**情境一（收藏）**：使用者在 IG 或 Google Maps 上滑到感興趣的餐廳，想快速存進自己的口袋名單，並依自己的邏輯分類（如「約會」「家庭聚餐」「一人食」）。

**情境二（查詢）**：使用者當下人在某個城市/區域，要決定去哪吃，想依自己的標籤/條件（也包含其他使用者標註的公開特色標籤，如「辣度」「氛圍」）快速篩選出想去的餐廳。

**地理範圍**：使用者指定的城市或更小區域，非全國性。

## 4. 候選方案清單（不收斂）

**方案 A：純網頁版 + 複製文字輔助新增**
使用者從 Google Maps / IG 複製店名、地址等文字，貼到網站的新增表單，系統做輕量文字解析預填欄位，使用者補齊分類與自訂標籤。純網頁操作，不涉及瀏覽器擴充套件或手機整合。

**方案 B：一鍵收藏（瀏覽器擴充套件 / 手機分享功能）+ 網頁後台**
在 IG、Google Maps 瀏覽當下，透過瀏覽器擴充套件按鈕或手機系統的「分享」功能，直接把連結丟進系統，自動解析並加入口袋名單；網頁端負責瀏覽、標籤管理、篩選查詢。

**方案 C：no-code 輕量驗證原型**
用 Notion / Airtable 之類工具手動建立餐廳資料庫與標籤系統，使用者手動複製貼上輸入資訊，先驗證「自訂標籤+篩選」的核心價值，不寫任何程式、不做自動解析，開發成本最低但體驗最陽春。

## 5. 可行方案（含初步評估）

**選定方向：方案 A（純網頁版 + 複製文字輔助新增）**

選擇理由：專案明確定位為「先做網站、不做 App」，排除了方案 B 需要的瀏覽器擴充套件/手機分享整合；方案 C 的 no-code 驗證雖然開發成本最低，但不是真正的網站產品，且使用者已表態要做網站而非先用 no-code 工具驗證。方案 A 在「不用打完整資料」與「不產生外部 API 費用」兩個限制下是可行的折衷。

**MVP 具體做法**：
- 新增餐廳流程：使用者複製「店名 + 地址」等文字區塊 → 系統用簡單文字解析（換行/關鍵字規則）預填欄位 → 使用者手動補齊分類、自訂標籤
- 不串接 Google Places API 或其他付費地點查詢服務。曾評估「只複製店名」的作法，但單一店名無法唯一定位（同名分店問題），需搭配地址一起複製才能不依賴外部 API；也評估過截圖 OCR 辨識，但準確率與開發複雜度都不如直接複製文字
- 地圖視覺化：可用開源地圖底圖（如 OpenStreetMap + Leaflet 之類的免費方案）顯示餐廳位置。**注意**：底圖顯示與「地點搜尋/geocoding」是兩件不同的事，前者免費方案成熟，不等於後者的 API 費用疑慮已解決
- 標籤系統：同時支援個人私有標籤與公開特色標籤
- 評論評分：初步建議簡化為個人筆記/評價，不做公開評論系統，降低審核、防灌水等複雜度（此點為初步建議，非使用者已定案）

**技術/時間/成本初步評估**：
- 前端/後端技術棧：不預設特定框架，留給後續 `system-design` / `dev-setup` 階段決定
- 需要資料庫儲存餐廳資料、標籤、使用者的口袋名單
- 文字解析屬輕量字串處理，開發複雜度低
- 因明確排除外部付費 API、且功能刻意簡化（無自動地點解析、無公開評論審核機制），MVP 整體開發複雜度偏低，時間成本可控，適合先驗證想法

**待釐清事項（留待 `requirement-scoping` 階段收斂）**：
- 帳號登入系統是否為 MVP 必要功能——口袋名單若要持久化、跨裝置使用，理論上需要，但本階段對話尚未問完就被使用者中斷，未定案
- 公開特色標籤如何避免濫用/灌水
- 文字解析規則的穩健度——不同來源複製出來的文字格式不一致（IG 貼文 vs Google Maps 分享文字），解析規則可能需分別處理或保留使用者手動修正的空間
- 評論評分功能的最終範圍（個人筆記 vs 公開評論）尚未由使用者定案，僅為本階段初步建議

# Dependencies, Risks & Constraints — 找餐廳網站

> SDLC Phase 2 步驟 10 產出。搭配 `docs/requirements-spec.md` 閱讀。專案為全新構想（無既有系統），本清單由 Lead 直接盤點，未派 agent 調查。

## 技術依賴

- **帳號認證機制**：需要密碼雜湊儲存、session 或 token 管理，技術選型留待 `system-design` 階段決定
- **資料庫**：需支援使用者表、餐廳表（全站共享）、使用者—餐廳收藏關聯表、私人標籤表、公開標籤表、標籤套用關聯表、筆記表等多對多關聯
- **地圖底圖服務**：需要免費地圖底圖方案（如 OpenStreetMap 類）顯示餐廳位置，僅用於「顯示地圖」，不涉及地點搜尋/geocoding API 費用問題，選型留待 `system-design` 階段
- **文字解析邏輯**：新增餐廳流程依賴的複製文字解析規則（非外部依賴，但屬於需要仔細設計的核心邏輯）

## 風險

| 風險 | 說明 | 影響範圍 |
|---|---|---|
| 重複餐廳 | 全站共享資料庫下，不同使用者對同一間店可能各自新增，造成重複資料；本版僅在新增時提示「可能已存在」，不做強制去重 | 可能導致同店有多筆記錄、標籤與收藏分散 |
| 資料所有權 | 餐廳基本資料的編輯/刪除限制在原始新增者；若原始新增者刪除該餐廳，會連動移除其他使用者的收藏記錄 | 需要在介面上明確提示，避免誤刪影響他人 |
| 公開標籤治理 | 任何使用者都可對任何餐廳套用/新增公開標籤，僅有基本過濾規則，無人工審核 | 可能出現不準確或惡意標籤，需後續迭代觀察是否要加審核機制 |
| 文字解析準確率 | IG 貼文與 Google Maps 分享文字格式差異大，簡單解析規則可能誤判欄位 | 已透過「使用者確認/修改預填結果」機制緩解，但體驗會受解析準確率影響 |
| 地點正確性 | 不透過官方地圖 API 驗證地址，地址完全依賴使用者複製貼上的文字 | 地圖定位可能不準確或無法定位 |
| 冷啟動 | 全站共享資料庫與公開標籤的價值都仰賴一定的資料/使用者規模 | MVP 初期資料量少時，「搜尋全站餐廳」的實用性有限 |

## 限制

- 不使用付費地圖/地點查詢 API，地點資訊完全仰賴使用者複製貼上的文字與免費地圖底圖服務的資料完整度
- 純網站形式，收藏新餐廳需要使用者手動複製貼上文字，沒有原生分享整合（App/瀏覽器分享功能不在本版範圍）

## 待 system-design 階段決定的技術選型

- 前後端技術棧
- 資料庫選型
- 地圖底圖服務選型
- 密碼雜湊演算法、session/token 機制選型
